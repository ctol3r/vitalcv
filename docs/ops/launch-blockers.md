**Closed 2026-08-08:** item **#14** (live revocation registry non-functional) — opened and closed the
same night by PR #1129 (`012429e2d`). All three breaks fixed: **(a)** `model StatusListState` added
with migration `20260808000000_status_list_state` (one additive `CREATE TABLE`, SQL generated by
`prisma migrate diff` so column names derive from the schema); **(b)** `GraphCascader` now delegates
to `setRevoked(artifactId)` and the no-op `setRevocationBit` is deleted rather than left as a trap;
**(c)** `/api/credentials/status-list` added to `shouldSkipTenantContext` as an exact path.

*Verified in production* at 02:06Z on `api.vitalcv.com`, not merely merged: the route returns **200**
(was 401), serving a `BitstringStatusListCredential` under the VC 2.0 context with
`credentialSubject.type: BitstringStatusList`, `statusPurpose: revocation`, an `encodedList` that
decodes to exactly **131,072 bits** (the W3C §4.1 minimum), and the reserved demo bit reading 0. The
200-vs-500 distinction is what proves the migration applied — a 500 would mean the guard fix landed
while the manager still threw.

*Regression cover:* 7 integration tests exercising the real DB paths, asserting the bit a verifier
decodes out of the served credential rather than the mechanism that set it. Each was proven to catch
its bug by re-injecting the original code. Note the harness divergence found while closing this:
**`backend-tests.yml` builds its DB with `prisma db push` from schema.prisma, while production runs
`prisma migrate deploy` from migration files** — so a model added to the schema *without* a migration
passes CI and fails production. That divergence is why (a) survived; add both, always.

*Still open, deliberately:* `// @ts-nocheck` remains on `statusListManager.ts` and `graphCascader.ts`.
Removing it surfaces unrelated pre-existing errors and belongs in its own PR — but that suppression
is exactly why a `undefined` Prisma model went unnoticed for a whole wave, so it is worth doing.

**Closed 2026-08-07:** item **#11** (revocation registry on Bitstring Status List + VC 2.0 pinning).
Both stated conditions are met: `apps/status-api` was ported from StatusList2021 to W3C VC 2.0
`BitstringStatusList` and its verifier now **fails closed** — every failure mode (unfetchable,
malformed, wrong format, purpose mismatch, expired list, out-of-range index) returns `unverifiable`
with a typed code, replacing a predecessor path that returned *not-revoked* on decode failure
(PR #1120, `950300c11`; 62/62 tests incl. a 22-fixture sweep proving no failure reads as
not-revoked). Demo credentials now issue a spec-correct `BitstringStatusListEntry` against a
reserved status bit instead of borrowing a real artifact's bit (PR #1124, `b1507c28c`).
`apps/api/backend` was already Bitstring/VC 2.0 from Wave 40.
**Scope note — read this before treating #11 as progress on revocation.** #11 was written against
`apps/status-api`, and that is exactly what was fixed. But `apps/status-api` has **no `Dockerfile`
and no `railway.toml`**, appears in no deploy workflow, and **is not deployed** — it is referenced
only by `monorepo.yml` for build/test. The live `/api/credentials/status-list` is served by
`apps/api/backend/src/routes/statusList.ts`, a different implementation, and that one is **broken
three ways** — see open item #14. So #11 closing means *the format and the verifier are now correct
in a service nothing runs*. It does **not** mean revocation works; end-to-end, it does not work at
all today.
