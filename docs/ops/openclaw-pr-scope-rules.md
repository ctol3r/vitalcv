# OpenClaw PR Scope Rules
**Authority:** openclaw-governance-hardening.md  
**Updated:** 2026-05-07  
**Use:** Applied before generating every task package

---

## Purpose

These rules prevent OpenClaw from generating task packages whose blast radius exceeds what Codex can safely verify in a single audit pass. Large PRs, cross-domain PRs, and hidden-drift PRs are the primary source of architectural degradation in fast-moving repos.

---

## Rule 1 — One Concern Per PR

A PR may address exactly one logical concern. If implementing a feature also requires fixing a bug, those are two PRs.

**Allowed in one PR:**
- A new feature and its tests
- A bug fix and its regression test
- A copy change and its copy test
- A CI gate and its documentation

**Requires splitting:**
- A feature + an unrelated bug fix
- A copy fix + an API route change
- A schema change + the feature that uses it
- An RBAC fix + a UI component change

---

## Rule 2 — Maximum File Count

| PR Type | Max Files | Exception trigger |
|---|---|---|
| Copy / docs | 5 | None |
| Single component | 8 | None |
| Feature with tests | 12 | None |
| Full feature wave | 15 | Scope justification required |
| Any PR | > 15 | Claude Desktop review required before task generation |

When a task package exceeds 15 files, OpenClaw must split it into sequential dependent PRs before generating any implementation prompt.

---

## Rule 3 — Domain Isolation

VitalCV has these distinct product domains. A single PR may cross at most **one domain boundary** (i.e., touch files in at most two domains when the crossing is justified):

| Domain | Key files |
|---|---|
| **Auth / RBAC** | `middleware.ts`, `lib/auth/` |
| **CRS / Scoring** | `packages/crs/` |
| **Source Adapters** | `packages/source-adapters/`, `packages/trust-state/` |
| **Issuer / PSV Trust** | `lib/issuer-verification/`, `packages/psv/` |
| **Clinician Product** | `app/clinician/`, `app/onboarding/`, `app/passport/` |
| **Employer / Verifier** | `app/employer/`, `app/review/`, `app/verifier/` |
| **API Routes** | `app/api/` |
| **Design System** | CSS tokens, shared components, typography |
| **Commerce / Pricing** | `lib/commerce/`, `app/pricing/`, `app/(checkout)/` |
| **CI / Infrastructure** | `.github/workflows/`, `scripts/` |
| **Documentation** | `docs/`, `MEMORY.md` |

**Crossing two domains** in one PR requires explicit justification: "This PR crosses Auth and API because the auth guard is wired directly into the route handler and cannot be separated."

**Crossing three or more domains** in one PR is always split.

---

## Rule 4 — Required Scope Lock

Before generating any task package touching GUARDED or higher files, OpenClaw must produce a scope lock:

```
SCOPE LOCK — [PR title]
Date: YYYY-MM-DD
Classification: SAFE | GUARDED | HIGH_RISK | FOUNDER_REQUIRED

Files to change:
  [exact file path 1]
  [exact file path 2]
  ...

Files adjacent but NOT to change:
  [exact file path — reason not touched]
  [exact file path — reason not touched]

Domain(s) crossed:
  [domain 1]
  (optional: [domain 2] — justification: [one sentence])

Test requirements:
  [test file] must assert [specific behavior]

Codex audit focus:
  [specific check 1]
  [specific check 2]

Blast radius if this PR is wrong:
  [one sentence — what breaks]

Rollback path:
  [one sentence — how to revert]
```

---

## Rule 5 — Migration Isolation

Schema changes are always their own PR, always tagged FOUNDER_REQUIRED.

```
CORRECT sequence:
  PR-A (FOUNDER_REQUIRED): schema change only
  PR-B (GUARDED or higher): feature that uses new schema — depends on PR-A

INCORRECT (always split):
  PR-X: schema change + feature implementation
  PR-X: schema change + copy changes
  PR-X: schema change + API route changes
```

The migration SQL goes to `docs/migrations/YYYYMMDD_<name>.sql` — never auto-generated by prisma in a routine PR.

---

## Rule 6 — Docs Before Code for Architectural Changes

For any HIGH_RISK change or any change that introduces a new architectural pattern:

```
Step 1: Write the proposal to docs/ops/
Step 2: Link the proposal in the PR description
Step 3: Get confirmation (founder or Claude Desktop)
Step 4: Implement in the next session
```

A HIGH_RISK task package without a linked docs proposal is incomplete.

---

## Rule 7 — Demo Data Isolation

Demo fixtures, seed data, and demo profiles must live in isolated locations:
- `apps/web/lib/demo/` — web app demo fixtures
- `apps/api/backend/src/modules/demo/` — API demo modules
- `apps/web/__tests__/fixtures/` — test fixtures

Demo data must never appear in:
- `lib/` (outside `lib/demo/`)
- `app/` components directly (components receive props; fixtures are injected at the page level)
- API route handlers (routes call services; demo stubs live in service layer, not route handlers)

A task package that places demo data outside these locations is a scope violation.

---

## Rule 8 — No Silent Refactors

If a task includes a refactor (rename, restructure, extract), the refactor must be:
1. The only concern of the PR (no feature work bundled)
2. Justified in the PR body ("why now, why this structure")
3. Documented in the Knowledge Trust Graph if it changes a boundary

Silent refactors — changes that restructure files without being flagged as refactors — are the primary source of hidden architectural drift. Codex diff audit catches these if scoped correctly.

---

## Rule 9 — No "Fix Forward" on Security Regressions

If a merged PR introduced an auth/security regression (guard removed, RBAC bypassed, audit event dropped):
- Do not open a new "fix forward" PR
- Revert the original PR immediately: `gh pr revert <pr-number>`
- Root-cause the failure in the reverted state
- Open a new PR with the original change PLUS the fix

"Fix forward" on security regressions creates a window of vulnerability and an unclear git history.

---

## Rule 10 — PR Description Completeness

Every PR generated by OpenClaw must include:

```markdown
## Summary
[What changed and why — 2-4 sentences]

## Risk classification
[SAFE / GUARDED / HIGH_RISK / FOUNDER_REQUIRED]

## Scope lock
Files changed: [list]
Files NOT changed: [list]

## Truth contracts
[Which invariants this touches — or "No truth-contract changes"]

## Test coverage
[Which test file, what it asserts]

## What NOT changed
[Explicit list]

## Codex audit required
[ ] Implementation audit
[ ] Diff audit
[ ] Copy/truth audit
[ ] Migration audit (if applicable)

## Rollback
[One sentence: how to revert if this breaks something]
```

A PR description missing any of these sections is incomplete. Claude Code Terminal must fill in missing sections before opening the PR.
