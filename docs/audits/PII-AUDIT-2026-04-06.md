# PII & Compliance Audit: Passport Route + Employer Decision Surface

> **Date:** 2026-04-06
> **Auditor:** Claude Cowork (operator context)
> **Scope:** Public Passport endpoints, Employer Review surface, Public Share surface, Readiness screen copy
> **Verdict:** PASS with 3 actionable findings (1 P1, 2 P2)

---

## 1. Scope of Audit

This audit covers four surfaces where credential data is exposed to users or the public:

1. **Public Passport API** (`/api/passport/entity/[id]`, `/api/passport/npi/[npi]`)
2. **Employer Decision Surface** (`/api/employer-review/*`, `ReviewClient.tsx`)
3. **Public Share Surface** (`/p/[slug]`, `public.ts`, `publicProfile.ts`)
4. **Readiness Screen Copy** (`PassportWallet.tsx`, `InterviewClient.tsx`, `ReviewClient.tsx`)

PII defined as: SSN, date of birth, home address, personal phone, personal email, clinical/patient data.

## 3. Detailed Analysis

### 3.1 Public Passport API Endpoints

**Files:** `apps/web/app/api/passport/entity/[id]/route.ts`, `apps/web/app/api/passport/npi/[npi]/route.ts`

**Authentication:** None (public endpoints).
**Rate Limiting:** Not applied at the proxy layer (relies on backend).

These Next.js route handlers proxy to the backend `passportService.buildPassport()` and validate the response shape via `assertPassportData()`. The validation enforces the PassportData contract but performs **type checking only** -- it does not strip or redact fields.

**Data returned via PassportData:**

- Identity: entityId, displayName, NPI, specialty, entityType, status
- Authority: credentials with domain, type, issuer, dates, confidence
- Training: institution, degree, completion status, graduation year
- Standing: exclusion status, licensure status, PECOS enrollment
- Readiness: CRS score, blockers, gaps
- Sources: checked sources with timestamps

**PII exposure:** No SSN, DOB, home address, personal phone, or personal email is present in the actual data returned. The backend `passportService` assembles only credential/verification data. However, the route-level code performs no explicit field stripping. If the backend service were ever modified to include PII fields, they would pass through unfiltered.

**Finding F1 (P1):** The proxy routes rely entirely on the backend not including PII. There is no defense-in-depth allowlist at the route level. The `public.ts` share endpoint demonstrates the correct pattern: explicit field allowlisting with `ClinicianPiiVault` architecturally excluded from the query.

### 3.2 Public Share Surface

**Files:** `apps/api/backend/src/routes/public.ts`, `apps/api/backend/src/routes/publicProfile.ts`

**Authentication:** None (intentionally public).
**Rate Limiting:** 20 requests/minute per IP (sliding window).

These endpoints implement **exemplary data minimization** at three levels:

1. **Model exclusion:** `ClinicianPiiVault` is never queried -- architecturally unreachable from the public route.
2. **Field allowlist:** Only `first_name`, `last_name`, and `taxonomy[0]` are extracted from `ClinicianIdentity.data`. All other fields are silently discarded.
3. **Response contract:** `PublicProfileResponse` strictly defines the allowed output fields.

The slug-based share link uses opaque UUIDs, not bare NPIs or names. Revoked/suspended credentials are filtered out before response.

**PII exposure:** None. This surface is well-designed.

### 3.3 Employer Decision Surface

**Files:** `apps/api/backend/src/routes/employerActions.ts`, `apps/web/components/review/ReviewClient.tsx`

**Authentication:** Clerk user ID header (`x-clerk-user-id`) required on all routes except one.

**Data returned to authenticated employers:**

- Identity: displayName, specialty (no SSN, DOB, address, phone, email)
- Verification lanes: binary checked/unchecked indicators for NPPES, OIG/LEIE, state board, PECOS
- Acceptance history: prior organizational acceptances (portable format)
- Evidence packet: exportable ZIP/JSON with verification receipts

**Audit trail discipline:** All mutating actions (accept, request-refresh, route-to-review) write `AuditEvent` rows before returning 2xx. NPI is logged with partial redaction: `npi_prefix: subject.clinicianNpi.slice(0, 4) + '....'`.

**Finding F2 (P2):** `GET /api/employer-review/npi/:npi/refresh-requests` does not require authentication. While the data returned (refresh request status) is low-sensitivity, it reveals whether a clinician has pending refresh requests, which could be used for inference attacks. NPI is publicly known, but organizational activity around it should be protected.

**PII exposure in UI:** `ReviewClient.tsx` displays only displayName, specialty, and verification status indicators. Detailed credential data is behind accordion patterns. The component explicitly calls out what is and is not covered: "Not included: NPDB, DEA, board certifications, SAM.gov."

## 4. Recommendations

### F1 (P1): Add explicit field allowlist to passport proxy routes

**Current state:** `apps/web/app/api/passport/entity/[id]/route.ts` and the NPI variant pass through whatever the backend returns after type validation only.

**Recommended fix:** Add a `sanitizePassportResponse()` function that explicitly picks allowed fields before returning. Mirror the allowlist pattern in `public.ts`. This provides defense-in-depth so that if a backend change accidentally includes PII, the proxy strips it.

```typescript
// Example pattern (do not merge directly -- implement via Claude Code)
function sanitizePassportResponse(data: PassportData): PassportData {
  return {
    identity: {
      entityId: data.identity.entityId,
      displayName: data.identity.displayName,
      npi: data.identity.npi,
      specialty: data.identity.specialty,
      entityType: data.identity.entityType,
      status: data.identity.status,
    },
    // ... explicit picks for authority, training, standing, readiness, sources
  };
}
```

### F2 (P2): Authenticate the refresh-requests endpoint

**Current state:** `GET /api/employer-review/npi/:npi/refresh-requests` has no auth middleware.

**Recommended fix:** Add `requireClerkUserId` middleware to this route, consistent with all other employer review routes.

### F3 (P2): Add PII-exclusion type guard to PassportData contract

**Current state:** `PassportData` in `passport-contract.ts` defines what fields *should* be present but does not type-enforce the absence of PII fields.

**Recommended fix:** Add a compile-time `NeverPII` branded type or a `StripPII<T>` utility type that causes type errors if SSN, DOB, homeAddress, personalPhone, or personalEmail fields appear in the contract. This makes PII leaks a build-time failure.

---

## 5. Overall Assessment

The passport route and employer decision surface do **not currently leak PII**. The `ClinicianPiiVault` is architecturally isolated from public routes, and all user-facing components display only credential verification data (NPI, specialty, license status, enrollment status, readiness scores).

The public share surface (`/p/[slug]`) is the strongest implementation, with three-layer data minimization. The passport proxy endpoints are the weakest, relying solely on backend behavior with no route-level defense.

All readiness screen copy is accurate, transparent about scope and limitations, and free of prohibited terminology or false compliance claims.

**No remediation is required before pilot deployment**, but F1 should be addressed before any production scale-up to maintain defense-in-depth.
