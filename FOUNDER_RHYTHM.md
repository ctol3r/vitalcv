## The Core Problem
You are drowning in infinite tasks because you treat building, selling, and operating as equal priorities.
They are not equal. Selling is survival. Building is debt service. Operating is overhead.

---

## The Hierarchy (engrave this)

```
1. SELL       → creates revenue
2. FIX        → removes blockers to selling
3. BUILD      → only what customers ask for
4. DOCUMENT   → only when it helps someone buy or use
5. EVERYTHING ELSE → do not do
```

If you are not doing 1 or 2, you need a reason.

## Daily Operating Rhythm

### Morning (30 min, before anything else)

**7:00–7:30 AM**
1. Check email + LinkedIn + DMs for replies to outreach (5 min)
2. Reply to every response immediately (10 min)
3. Send 3 new outreach messages (cold or follow-up) (10 min)
4. Check if demo path still works — enter one NPI, confirm passport loads (5 min)

That's it. Then start your actual work.

### Work Block 1 (2 hours, 9–11 AM): SELL

Pick ONE of:
- A: Run a pilot report (send a real NPI readiness check to an interested employer)
- B: Write + schedule one LinkedIn/Twitter post
- C: Have a 20-minute demo call
- D: Send 10 personalized DMs to travel nurses or recruiters

Only one. Do it completely. Then stop.

### Work Block 2 (2 hours, 1–3 PM): FIX or BUILD

**If a demo is broken**: fix it. Nothing else. P0 bugs only.
**If a user asked for something**: build exactly that, nothing more.
**If nothing is broken**: pick one item from REAL_MVP_BOUNDARY.md "Week 2" list.

Rule: If you can't ship it in 2 hours, break it into a smaller piece.

### Afternoon (1 hour, 4–5 PM): OPERATE

- Check analytics (NPI lookups, signups, time-on-site)
- Log what happened today in memory/YYYY-MM-DD.md
- Update DEALS_LOG.md with any employer/recruiter conversations
- Prep tomorrow's outreach (write 3 messages, queue them)

### Evening: Off

Do not build at night. Your judgment degrades. Decisions made after 8 PM are usually wrong.
Exception: if a P0 production issue is breaking the demo path.

## Build Cadence

### What triggers a build session
Only one of:
1. A real user reported a specific broken thing
2. An employer pilot requires a specific capability to close
3. The demo path broke

### What does NOT trigger a build session
- "It would be cool if..."
- "We should also have..."
- "What if we added..."
- Any architecture-level refactor
- Any new integration not asked for by a paying customer
- Anything in the "NOT MVP" section of REAL_MVP_BOUNDARY.md

### The 2-hour rule
If a fix or feature takes more than 2 hours, either:
- Break it into a smaller piece, or
- Defer it until after the first pilot closes

## Demo Cadence

### Always be ready to demo in 5 minutes
The demo path (homepage → NPI entry → passport → holder dashboard) must work at all times.
Test it yourself every morning. If it breaks, that is your entire day.

### Demo schedule target
- Week 1: 1 informal demo (recruiter or clinician, anyone willing)
- Week 2: 2 demos (at least 1 employer)
- Week 3: 3 demos, 1 formal pilot walk-through
- Week 4+: demo every week until a pilot closes

### After every demo, write 3 sentences
1. What confused them most
2. What excited them most
3. What question they asked that you couldn't answer

These three sentences drive your next build session.

## The 3 Signs You're Drifting

→ Stop. Go send outreach.

**Sign 2: You haven't talked to a real user in 3 days**
→ Stop. Go post in Reddit or DM 5 nurses.
