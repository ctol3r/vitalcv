Materialization hierarchy · executable vs. non-executable

the boundary is the first fact

The most important distinction in the VitalCV architecture is not between states within the executable zone — it is between the executable zone (live, partial) and the non-executable zone (spec, orphaned, superseded). An institutional reviewer or developer should be able to determine which zone a surface is in before reading anything else about it.

01

PR state mapping · four PR states → materialization state

PR lifecycle determines product state · always

A surface's materialization state is determined by the state of its PR, not by intent or design. A merged PR with a missing topology update is a partial surface, not a live one. A draft PR with a routed component is an orphan, not a partial. PR state is the ground truth — everything else follows from it.

What it means for the surface

Draft PR
Work in progress. Component may exist in a feature branch but is not reachable from the main product. No product surface exists yet.
Spec — treat as design artifact until merged. No route should be declared from a draft branch.

Open PR
Implementation complete on the feature branch. Route, component, and data are present but not yet in main. Not in the live product.
Partial (branch-local) — can be demonstrated from the feature branch, but topology map should not be updated until merge.
Conduct sync protocol review in PR. Do not update topology map until merge completes.
Merged PR
Code is in main. Route is accessible. All four sync steps must now be verified against the merged state, not the branch state.
Live — if all four sync steps pass on the merged main branch. Partial if any step fails after merge.
run sync protocol on merged main. Update topology map. Log state transition.
Closed (unmerged)
PR abandoned without merge. If any code was pushed to main before closure, that code is now disconnected. Any route added from this branch must be removed.

leave orphaned routes in app.jsx. Remove route, add orphan annotation, update topology map.
02

Operational reality checks · nine checks · three phases

run at any time · each returns pass or fail

Nine concrete checks that verify operational truth. Each check is runnable by inspection or grep — no automated tooling required. Run these checks after every PR merge, before every demo, and whenever the topology map is updated. A surface that fails any check is not live regardless of what the topology map says.

Nine reality checks · three phases · pass / fail verdict per checkrun per wave · per merge · per demo
Phase 1 · Route
Route resolves without 404
Navigate to the declared path in the running product. Does it render? A 404 or blank screen = fail.
state = orphaned or spec
Phase 1 · Route
Route is reachable from navigation
Starting from the product home, can you reach this route through at least one nav path? No dead-end approaches.
state = partial (unreachable surface)
Phase 1 · Route
No superseded file at same path
Grep app.jsx for the path. Only one component should be assigned to it. grep -n "/activate" — if two imports match, one is wrong.
state = drift event · remove superseded
Phase 2 · Component
No console errors on render
Open the surface in browser. Check console. Any error = fail. Warnings are acceptable if they are known and annotated.
state = partial · fix errors before live
Phase 2 · Component
No TODO handlers on interactive elements
grep -n "TODO" src/ in the component file. Any TODO in a click/submit handler on a visible element = fail.
state = partial · wire or hide element
Phase 2 · Component
All child imports resolve
Build the component in isolation. Any missing import = fail. Watch for components that import superseded wave files.
state = broken · resolve imports first
Phase 3 · Data + Topology
All data values labeled real or mock
grep -n "// MOCK" src/ — every hardcoded value should appear. Any unlabeled hardcoded string/number in a live surface = fail.
state = drift · add // MOCK or connect data
Phase 3 · Data + Topology
UI copy matches implemented features
Read every button label, status message, and section heading in the surface. Does each one describe a feature that exists? Any mismatch = fail.
state = drift · update copy or build feature
Phase 3 · Data + Topology
Topology map reflects current state
Cross-reference the topology map's state for this route against the results of checks 1–8. Map must match reality. Any discrepancy = map is stale.
topology drift · update map immediately
03

Topology-truth language · seven substitutions · binding vocabulary

language is an implementation claim · treat it as such

The language used to describe a surface is itself an implementation claim. Calling a spec-only surface "ready" is a materialization lie. Calling an orphaned route "deprecated" obscures its actual state. Seven substitutions that replace speculative or ambiguous language with operational truth.

Phrase to retire
Replacement
Why the original is dishonest
"Coming soon"
"Not built yet." If it's in the nav: remove it. If it's in documentation: label it spec.
"Coming soon" implies a commitment and a timeline that may not exist. It's a marketing phrase, not an implementation state.
"Deprecated"
"Superseded by wave{N}" or "Orphaned — no active route." Name the specific state.
"Deprecated" is vague — it doesn't say whether the surface is still reachable, what replaced it, or whether it carries a risk of being navigated to.
"In progress"
"Partial — [specific incomplete feature] not yet built." Name what's missing.
"In progress" could mean draft, open PR, or partial. Without naming the incomplete part, a reviewer cannot assess the risk of using the surface.
"Planned"
"Spec only — no route, no component." Spec is the honest state.
"Planned" implies a roadmap commitment. Spec means it exists in design. These are different claims. Only one is true at time of writing.
"Live" (without sync verification)
"Live — passed sync protocol [date]." The date matters. Live degrades if not re-verified after changes.
Calling a surface live without running the sync protocol is a guess, not a state. Live is a verified claim, not a declaration.
"Legacy"
"Superseded — [wave{N}] is canonical." Name the canonical replacement.
"Legacy" doesn't tell a developer whether the route is still active, whether it imports the superseded file, or whether it needs to be cleaned up.
"Experimental"
"Partial — boundary markers required on surface." Experimental and partial are the same state. Use the canonical term.
"Experimental" is a disposition, not a state. It doesn't specify what's incomplete or what would make it live. Partial with named incomplete features is honest.
04

Executable-boundary semantics · what can run · what cannot

boundary is always the first fact · never inferred

The executable boundary is the most important structural boundary in the VitalCV architecture. Everything on the executable side of the boundary can be opened in a browser, navigated to, and evaluated by an institutional reviewer. Everything on the non-executable side cannot — it is design, documentation, or disconnected code. The boundary is always labeled, never implied.

Live route · live component · real or labeled data

State claims

Reality check cadencerun often · 9 checks · fast by design
After every merge
run all 9 checks on the affected routes within the same session as the merge · update topology map before closing the session
Before every demo
Run checks 1, 2, and 4 (route resolves · reachable from nav · no console errors) on every surface in the demo flow. demo a surface without checking 1, 2, and 4
Before every PR merge
Run checks 5 and 7 (no TODO handlers · all data labeled) as part of PR review. These are the two most common sources of post-merge drift.
Monthly audit
Run all 9 checks on every route in the topology map. Any failure triggers an immediate state reclassification. The map must never be more than 30 days stale.
