VitalCV · Attribution Integrity System · v2026.05.21
Every action attributed. Every record owned.
Four attribution tiers, four audit legitimacy levels, bounded pilot semantics. No action is credited to a party that did not perform it. No record claims authority beyond its actual provenance.
§1
Attribution hierarchy · Four tiers.
Every event in VitalCV is owned by exactly one tier. The tier determines what can be claimed, what cannot, and what the attribution chip renders. Cross-tier attribution is not permitted. Use the Tweaks panel to isolate each tier.
Tier 1
System
Can claim: executed checks, computed confidence grades, recorded state transitions, triggered retries. All system actions are timestamped machine records.
Cannot claim: review, approval, authorization, judgment, deployment sign-off. System actions attest to occurrence — not human judgment.
System Auto · NPPES Check 14:01:33
Tier 2
Reviewer
Can claim: reviewed specific records, exercised judgment on exceptions, acknowledged stated limitations, escalated blocking items. Named person + timestamp required.
Cannot claim: organizational authorization, deployment authority, source-level verification. Reviewer attests to their judgment — not the truth of underlying data.
S. Chen Reviewer 14:22:07
Tier 3
Organization
Can claim: authorized deployment within a stated scope and window, accepted named limitations. Org acts through a named individual with a named role.
Cannot claim: individual review actions, source-check results, system verification. Org authorization confirms the decision — not the evidence state that informed it.
Mercy Health Org · Auth 09:15:44
Tier 4
Record
Can claim: a snapshot of what tiers 1–3 did, when, and with what stated evidence. Immutable once written. Deployment record 045-A created at 15:00.
Cannot claim: validation of the actions it records. A record attests to occurrence — not to the accuracy of underlying data at time of action.
Record Immutable · 045-A 15:00:02
§2
Accountability language system.
All review and operational copy follows a single formula. Actor must be named. Action must be specific. Scope must be bounded. Timestamp must be exact. Vague attribution is a form of fake attribution.

§3
Bounded audit semantics · four legitimacy levels.
A machine log is not equivalent to a human attestation. An org authorization is not equivalent to source verification. The system never conflates levels. Each level attests to exactly what it can defensibly claim.
L1
Machine record · System tier
Automated event log. Records that something happened, when, and with what system-observable result. Attestation scope: occurrence only. L1 records are not human-reviewable in the sense of judgment — they are timestamped state captures from deterministic processes.
actor:System · action · scope · timestamp · raw result
L2
Human attestation · Named reviewer
A named individual reviewed specific records and exercised judgment. Attestation scope: judgment only. The reviewer attests to their decision given the evidence shown to them — not to the accuracy of the underlying source data at query time.
actor:named person · role · record IDs reviewed · judgment type · timestamp
L3
Organizational authorization · Named authorizer
A named person at the organization authorized a deployment within a stated scope. Attestation scope: decision only. Org authorization attests to intent to proceed — not to the completeness or currency of evidence reviewed.
actor:named org · authorizer name+role · roster/scope · deployment window · timestamp
L4
Deployed record · Immutable snapshot
A snapshot created at deployment time, capturing L1–L3 events and confidence grades as they stood at that moment. Attestation scope: occurrence chain only. The record attests that these events happened in this sequence — it does not re-validate the evidence that informed them.

The audit log is append-only. Each row's actor, action, scope, and timestamp are set at creation and cannot be amended. Corrections are new rows — not overwrites — carrying action:correction and a reference to the original event ID. The log records what happened, not what should have happened.
§4
Institution-ownership architecture.
The organization is the accountable party for every deployment decision. VitalCV surfaces evidence and records actions. VitalCV never owns the deployment. The system never authorizes. The organization always does.

1
Org name must come from the org record. Never hardcode institution names. The ownership block reads from org.name, org.id. An org without a record cannot own a deployment — show an "owner not set" placeholder, never a default.
2
Authorization requires a named individual. "Mercy Health authorized" is incomplete. The authorizer must be a named person with a stated role. The organization acts through people — not as an abstract entity.
3
Scope must be explicit. Authorization is scoped to a specific roster and a specific deployment window. "Authorized" without scope is structurally insufficient. It does not authorize future rosters or extend past the window.
4
VitalCV is a vendor, not an authority. System-tier events are labeled System — not "VitalCV," not "AI," not the product name. The vendor is the tool; the organization is the accountable party.
5
Authorization does not upgrade confidence grades. If confidence was Grade B at authorization time, the record reflects Grade B. Org sign-off authorizes the decision to proceed with known limitations — it does not improve the evidence state.
§5
Pilot attribution patterns.
Pilot sessions require persistent, non-removable attribution of their bounded context. Pilot records cannot be cited as production evidence. Pilot confidence grades are evaluation artifacts, not operational attestations.

§6
Implementation guidance for Claude Code.
Attribution event structure
1
Every audit event requires: actor (tier + identity), action (enum: check|review|authorize|record|correction), scope (record IDs or roster ID), timestamp (ISO 8601), basis (what evidence supported the action). All fields are required — no optional attribution fields.
2
The actor field accepts exactly: {tier:'system'}, {tier:'reviewer', name, role}, or {tier:'org', name, authorizer:{name, role}}. No other shapes are valid. Reject events with unrecognized actor shapes at write time.
3
Audit events are append-only. No update or delete. Corrections use action:'correction' with corrects: eventId. The original event remains in the log — correction rows appear inline below the original, visually linked by the event ID reference.
Org ownership representation
1
The deployment owner block reads session.org.name, session.org.id, session.org.authorizer.name, session.org.authorizer.role, session.org.authorizedAt. If session.org is null or incomplete, render a placeholder: "Deployment owner not set — authorization required before advancing."
2
Never use the vendor name as an actor. System-tier events render as "System." Not "VitalCV," not "AI," not the product name. The vendor is the infrastructure — never the accountable party.
3
Authorization copy must include roster ID and deployment window. If either is missing, emit a gate-level warning: "Authorization scope is required before the deployment gate can advance." Do not allow gate advancement with incomplete authorization scope.
Pilot context rules
1
Pilot context is set at session level: session.context = 'pilot' | 'production'. All components read this flag. The pilot banner renders whenever session.context === 'pilot' and cannot be dismissed within that session.
2
In pilot context: gate copy replaces "deploy" with "evaluation run." Audit log rows carry pilotContext: true. Exported records include a PILOT — NOT FOR OPERATIONAL USE header. These are structural requirements — not cosmetic. They prevent pilot records from being used as production evidence.
3
If a production deployment references a record where record.pilotContext === true, reject with: "This record originates from a pilot session and cannot be used as production evidence." Never silently include pilot records in production audit chains.
Anti-patterns · never implement
✗
Auto-advance on timeout. If a reviewer does not act within N minutes, the system must not advance the accountability step automatically. It must wait, or emit a non-blocking reminder. Human judgment steps cannot be skipped by inaction.
✗
Silent step transitions. No accountability step changes without a visible audit log entry and a chip update in the workspace header. Every ownership transition is a named event — never a background state change.
✗
Anonymous audit rows. An audit log row showing "Reviewed" without a named reviewer, or "Authorized" without a named authorizer, is structurally invalid. Render a warning row instead: "Attribution missing — this event cannot be used as evidence."
✗
Confidence upgrade post-authorization. Org sign-off does not change confidence grades. Do not re-derive or re-display higher grades after authorization. The grade at authorization time is the grade in the permanent record. Authorization accepts the evidence state — it does not change it.
