Materialization state legend · five states · binding vocabulary

left border + badge · always both · never implied

Every wave, route, and surface carries a materialization state. The state is always rendered — never inferred from context. A reviewer reading any surface knows immediately whether it reflects a live implementation, a partial build, a specification, an orphan, or a fixture.

Live
Fully materialized. Routes are connected, views are rendered from real data, state is managed, and the surface is accessible at its declared path.
Left border: solid 3px var(--m-live). Badge: solid green outline. Navigation to this surface is safe and expected.
Partial
Component exists, but incomplete. The route resolves. Some views render. Data may be mocked. At least one declared feature is not yet built.
Left border: dashed 3px var(--m-partial). Badge: dashed amber outline. Navigation is permitted but boundary must be visible.
Spec only
Designed but not built. Exists in design artifacts, PRDs, or wave specs. No route. No component. No data. Conceptual only.
Left border: dashed 3px var(--ink-300). Badge: dashed slate outline. Navigation to this surface must not exist in the live product.
Orphaned
Built but disconnected. Component exists in codebase but no active route leads to it. May have been superseded, refactored out, or abandoned mid-wave.
Left border: solid 3px var(--m-orphan). Badge: warm amber-red. Must not appear in navigation. Must be labeled if shown in design artifacts.

04

Conceptual hallucination prevention · what not to do · always

if it isn't built · don't navigate to it · ever

Conceptual hallucination occurs when a surface presents navigation, features, or data that does not exist in the materialized implementation. It is the most damaging form of dishonesty in an institutional product — because institutional reviewers make decisions based on what they see. A speculative navigation link is a lie. An unmocked data value is a lie. A feature described in UI copy that doesn't exist is a lie.

Don't do this Do this instead State
Navigation link to D45 NPI Resolution from product nav
Remove the link. NPI Resolution is spec-only — no route, no component, no data.
Spec
"All 12 sources live" status when only 5 sources are wired
"4 of 5 sources responding" — only show the sources that actually exist in the implementation.
Partial
PR-B Crypto Verifier link in the verifier nav
No link. The PR-B design is superseded. Wave23 is canonical. Orphaned surfaces have no navigation entry point.
Orphaned
Admin "Bulk revoke" button that calls a non-existent endpoint
Hide the button or label it "coming in next wave." Never render an action that cannot complete.
Partial
Activation v1 accessible via back-navigation from v2
Remove v1 route from active navigation. v2 is canonical — v1 is orphaned and should not be reachable from product flow.
Orphaned
"Deploy to production" button on pilot surfaces
Show the button only when all readiness checks pass AND the surface is in production mode, not pilot mode.
Partial
Design artifact (D45-D55) treated as a navigable product surface
Label all design artifacts in the op-bar: "Design artifact · not a product surface." Never link from app.jsx or include in the prototype route map.

05

Implementation guidance · Claude Code · binding rules

topology · boundary · hallucination prevention · all binding
Route hygieneno speculative links · canonical routes only
Navigation links
only link to routes with a live or partial materialization state · link to spec-only or orphaned surfaces from product navigation
Orphaned routes
import orphaned view components in app.jsx · add orphaned routes to the router · retain files for reference, not for navigation
Superseded views
When a wave supersedes a prior view (e.g. wave14b supersedes wave14), the prior file stays in the repo but is removed from the router. The canonical version is always the highest wave number that is live.
Design artifacts
All D44-D55 HTML files are standalone design artifacts — they are not product surfaces and must not appear in app.jsx imports or the router. They may be linked from documentation, not from the product.
Boundary markers in codestate is always explicit · never inferred
Partial surfaces
Add a data-materialization="partial" attribute to the root element of any partial view. The boundary system reads this and renders the dashed corner tag automatically in design-artifact mode.
Mocked data
label all mocked data values with a // MOCK comment at the data source · pass mocked values into UI without a comment — mocked data becomes indistinguishable from real data within two wave iterations
Spec surfaces
If a spec surface must be rendered (e.g., for a walkthrough), add data-materialization="spec" and render the corner tag: "spec · not built." render a spec surface without the tag visible
Wave versioning protocolcanonical version is always the highest live wave
Canonicalization
When wave N supersedes wave M for the same surface, wave M is marked orphaned. The canonical route uses wave N's component. two waves active for the same route simultaneously
File naming
Use wave{N}-{surface}.jsx for wave files and view-{surface}.jsx (or view-{surface}-v2.jsx) for the canonical view component. Never rename a live view without updating all import sites.
Retirement
Before retiring a wave: (1) confirm no active route imports it; (2) confirm no navigation link points to it; (3) add a // SUPERSEDED by wave{N} comment at the top of the file. Do not delete — retain for reference.
Hallucination audit checklistrun before every wave release
Navigation audit
For every nav link: verify the route resolves, verify the view component is imported in app.jsx, verify the view is not marked orphaned or spec.
Action audit
For every button and CTA: verify the action has a handler, verify the handler connects to a real or explicitly mocked endpoint. render a button with a TODO handler in a non-partial surface
Data audit
For every data value in a live surface: verify it comes from a real source or an explicitly labeled mock. hardcode data values in live surfaces without a // MOCK comment
Copy audit
For every feature mentioned in UI copy: verify the feature exists in the materialized implementation. mention a feature in UI copy that hasn't been built — this is conceptual hallucination in text form
