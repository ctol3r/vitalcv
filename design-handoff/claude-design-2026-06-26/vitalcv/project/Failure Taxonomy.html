01

Five failure modes · five distinct surfaces

never collapsed into "something went wrong"
A · Source unreachabledegraded · upstream

The source didn’t answer in time.

A specific registry is slow or unresponsive. The rest of the system continues; this lane simply isn’t fresh. Receipts still issue with source.X.degraded=true recorded inline.

OwnerUpstream registry. Not VitalCV, not the holder.
User seesDashed lane chip · stale checked_at · honest age label.
ActionWait or retry. Anything older than the source’s last confirmed value is treated as not yet checked, not as adverse.
ExamplePECOS · p95 5.8 s · 2 m 54 s ago
B · Anonymous restrictionpolicy · not technical

This lane requires sign-in.

Some sources reveal protected fields only when the holder is authenticated. The check did not fail — it was not attempted under your identity. The lane is empty by design.

OwnerVitalCV policy + the holder. Authentication is required to ask.
User seesLane greyed out · “sign in to verify” affordance · no claim asserted.
ActionSign in (or have the subject sign in). This is not an outage.
ExampleDEA full registration · subject auth required
C · Infrastructure outageVitalCV-side

VitalCV is down.

A VitalCV service can’t serve this request right now. Existing signed receipts remain valid — they verify offline against did:web:vitalcv.health and don’t need our servers.

OwnerVitalCV. We name it. We page ourselves.
User seesBlack status banner · incident id · link to status.vitalcv.health · current SLO impact stated.
ActionIf holding a signed receipt, verify it against the public verifier — no VitalCV server needed. Otherwise wait.
Exampleinc-2026-0511-c · wallet API 5xx · 12 m elapsed
D · No adverse findingssuccess · not a failure

The source answered. Nothing was found.

The exclusion list / sanction registry returned an empty result. This is the desired outcome for a clean provider — and it is materially different from “we couldn’t check.” The receipt records the negative finding.

OwnerNo one. The system worked.
User seesSolid lane chip · “no findings · confirmed” · fresh checked_at.
ActionNone. This is the affirmative state. The receipt is signed and re-verifiable.
ExampleOIG-LEIE · 0 records · 10 s ago
E · Issuer unavailablecryptographic · the signing path

The signing key can’t be reached or trusted.

The most serious mode. The active signing key is unreachable, expired, or compromised. New receipts cannot issue until the issuer continuity plane recovers (active key, backup signer, or rotation). Existing signed receipts remain valid — until and unless one is explicitly revoked via Status List 2021.

OwnerVitalCV · keyholder quorum.
User seesInverted black banner across signed surfaces · “issuance paused · existing credentials unaffected unless revoked”.
ActionVerifiers: continue to trust existing receipts. Operators: rotate to backup signer per runbook.
Examplekey 4f2a unreachable · backup 8c91 ready · quorum 3 of 5 pending

03

Confusions to prevent

three pairs that look identical without the rules above
D ≠ A“Nothing found” in an exclusion list is a signed negative finding. “Source unreachable” is the absence of a check. Conflating them lets a degraded source masquerade as a clean record. The system never lets this happen — D is solid, A is dashed.
B ≠ C“Sign in to verify” is a policy gate; the user can resolve it themselves. “VitalCV is down” is a platform incident; the user can’t. We never tell a user to authenticate when the cause is our service.
C ≠ EAn ordinary outage suspends new work. An issuer-unavailable event suspends signing specifically — receipts already in the wild are not affected. The inverted register on E signals that this is the cryptographic plane, not the runtime plane.
