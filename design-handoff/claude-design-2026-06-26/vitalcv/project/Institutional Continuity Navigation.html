01

No dead ends · every state has a forward path

state → next step → language · always

For every state a user can reach, the system provides a visible next step. If the system must act before the user can proceed, the system says so explicitly — it does not leave a blank screen. If the user must act, the action is the only prominent element. Dead ends are a design failure, not an edge case.

04

Bounded simulation semantics · pilot vs. production · always labeled

honest about what is real · never magical

VitalCV operates in two modes during institutional onboarding: pilot (bounded, scoped, limited to the agreed NPI set) and production (full deployment, live data, organization-wide). Every surface is unambiguous about which mode it is in. Fake automation is never shown. Incomplete results are never presented as complete.

Pilot mode · bounded · honest
Pilot · Cedar Health · 10 NPIs · bounded scope
Pilot mode shows exactly what has been checked. No extrapolation. No projection. If 10 NPIs were submitted and 7 are verified, the surface shows "7 of 10" — not "70%" or a progress ring that implies completion.

always label every pilot surface with org name + scope
always show actual counts, never percentages as primary signal
present pilot results as production evidence
project forward from pilot data without labeling
Pilot scope: 10 NPIs · Cedar Health · R-2026-05-21
10 of 10 submitted · 7 verified · 3 pending
Production mode · live · full deployment
Production · Cedar Health · all clinicians · live
Production mode carries the full weight of institutional trust. Data is live. Chain is anchored. Every result is the current state of the source at the time of last check. Freshness age is always shown explicitly.

always show freshness age in production mode
always show source health indicator in production mode
confuse pilot results with production results in a shared view
show production data without the checked_at stack visible
Production · all clinicians · Cedar Health · live
checked_at 14:31:58Z · 22 s ago
Bounded simulation · what to show in a demo or pilot that isn't fully complete
Show actual data, labeled. If you have 7 of 10 results, show 7 of 10. Never show a completed ring or "all clear" status for incomplete data. The incompleteness is honest — it means the pilot is still running.
Label projections as projections. If the waste-visibility surface shows a projected annual saving, label it: "Projected based on pilot results." Never present a projection as a measured outcome.
05

Operational reassurance patterns · five situations · calm language

calm is earned · not performed

Reassurance in VitalCV is informational, not performative. It is never a green check on a completed action that didn't need confirming. It appears when a reviewer might reasonably wonder whether something went wrong — and it answers that question plainly. Reassurance is always specific. It names what is intact.

who is responsible for what · never implicit

A reviewer who opens a surface knows immediately whether they are expected to act, whether the system is acting, or whether the task belongs to someone else.

Implementation guidance · Claude Code · binding rules

continuity · recovery · ownership · simulation · all binding

These rules are binding on every surface in the institutional progression arc. Treat violations as bugs — not judgment calls. Every rule maps to a component behavior or a language pattern.

Progression Railpersistent · always visible · never collapsed
Placement
render at top of every institutional surface · below op-bar · above page content · hidden on mobile behind a menu
Completed stages
keep completed stage data in detail strip · mark with ✓ prefix · ink-0 background · remove or collapse completed stages
Active stage
ink-900 fill · white text · arrow connector to next stage · → running now state label
Future stages
always render future stages · opacity 0.45 · no data in detail strip · · pending state · hide future stages
Next stage
ink-50 background · · up next state · renders as visually distinct "approaching" state between active and future
No Dead Endsevery state has a forward path · no exceptions
Empty states
always show a next step in Zone C · if no action is available, show the auto-next pattern · blank Zone C
Error states
Zone A: plain-English description of the problem. Zone C: one action to resolve. error states without an action · error codes in Zone A
Blocked states
Use .ns-next.blocked pattern · name the blocker explicitly · show the automatic resolution path if one exists · blocked state without naming the cause
Completion states
Use .ns-next with "Next in arc" label · show what comes next in the progression arc · never a dead-end "complete" screen without a forward path
Interruption Recoveryvisible · honest · never silent
Left border
Encode interruption type in left border: dashed = source/network · solid warm = review blocked · solid green = recovered. always pair border with a plain-English message
Gap documentation
always name the gap duration explicitly · "17-minute gap documented" · present recovered state as if no gap occurred
Recovery language
Use "Picking up where we left off" for resumption. Use "Nothing was lost" for network recovery. Use "Back online" for connection restoration. use "Error resolved" or "Problem fixed" — name what is intact, not what was broken
Bounded Simulationpilot vs. production · always labeled · never faked
Pilot surfaces
always render pilot mode banner with org name, NPI count, and scope · present pilot data as production data
Projections
always label projections as projections · include basis: "Projected based on pilot results" · present projections as measured outcomes
Incomplete results
always show actual counts: "7 of 10" · show percentages as primary signal for incomplete sets · show progress rings implying completion
Review Ownershipexplicit · never inferred · chip on every blocking action
Ownership chip
render ownership chip on every surface with a blocking action · system / reviewer / org / shared · infer ownership from login state
Named reviewer
When a specific reviewer is assigned: name them in the surface. "This exception needs J. Martinez's decision." Not "a reviewer." use "a reviewer" when the name is known
Audit trail
record reviewer name + timestamp for every decision · surface this in the closed-stage detail strip · record only the decision, not the decider
