Degraded-state semantics · five non-confusable modes

Five modes. Three planes. One success.

Every failure VitalCV can render falls into five modes across three planes. The taxonomy is closed. Modes are visually non-confusable by frame alone — no reviewer ever needs to read prose to classify the mode. Mode D is success, not failure: verified absence of adverse findings. Infrastructure failures are visibly separated from subject findings; replay degradation is visibly separated from issuer degradation. Severity does not encode danger — it encodes which plane owns the recovery.

Contract
Every degraded mode is owned by exactly one plane. The plane is named on the artifact. A reviewer who reads only the mode letter and the owner line can route the incident to the correct responder without ambiguity. The subject plane (4) never owns a failure — findings about the subject are outcomes, not failures; absence of adverse findings (mode D) is a positive outcome rendered as a typed result, not a typed error.

Reading contract
Severity is a read-order property, not a danger ranking. S0 (success) reads first on a clean surface; S1–S4 read in increasing operational scope of the outage. A reviewer triages by reading the severity step and the plane simultaneously: severity tells them how much of the artifact is unusable; plane tells them which responder owns the recovery. Mode D is severity 0 because nothing requires recovery — the artifact is complete.

Recovery contract
Every degraded interval renders the six recovery stages visibly: STEADY → LAST CLEAN → ONSET → DEFER → RECOVER → STEADY. The σ-chain hash-linkage is never broken through degradation — a degraded node carries σ defer, not absence. The recovery anchor (last clean σ-ok node, stage 02) is named explicitly so a verifier can re-derive the pre-incident state offline. The "no subject claim altered" assertion at stage 04 is mandatory: it disambiguates operational degradation from data alteration.
P5 ·

Plane separation · what must never be conflated

infra ≠ subject · replay ≠ issuer
Boundary 1

Infrastructure failures ≠ subject findings

C
Mode C · haltVitalCV's verifier could not produce a receipt. The artifact is unavailable. No claim about the subject is made.
D
Mode D · successThe verifier produced a complete receipt. The subject has zero adverse findings. Verified absence is a finding.
A SaaS UI conflates these: "no data shown" reads identically whether the system failed or the subject is clean. VitalCV separates: ink-900 filled banner (infra) ≠ 2 px solid frame with count pill (success).
Boundary 2

Replay degradation ≠ issuer degradation

A
Mode A · σ deferUpstream source did not refresh. Issuer's σ-chain is intact; the freshness clock is what failed. Recovers on upstream availability.
E
Mode E · σ withheldIssuer's signing key is unavailable. Replay can resume only after quorum or rotation. The cryptographic plane is what failed.
Both modes "withhold a signature" but for categorically different reasons. A is paper + dashed (recoverable by waiting). E is ink-950 + diamond (recoverable only by cryptographic action). Glyph delta is categorical: chevron ≠ diamond.

Pairwise disambiguation contract
Every pair of modes is distinguishable by at least one categorical visual channel (frame style, frame weight, background, glyph, or plane attribution). The three historically dangerous pairs — D ≠ A (success vs stale), C ≠ E (infra vs cryptographic), A ≠ B (upstream vs policy) — each resolve at the frame level before the reviewer reads any prose. No mode can be reached visually from another by adjusting a single token. The visual distance is structural.
P7 ·

Institutional failure language · canonical phrasing

say · don't say · why
ModeSayDon't sayWhy
A Source unreachable · stale-but-signed · 47 m Error · could not load · failed to fetch Names the upstream owner. "Stale" is a freshness property, not a system error. The artifact remains binding for the pre-stale interval.
B Restricted to authenticated callers · sign in to view Access denied · forbidden · not authorized Restriction is a policy state, not a security event. The caller is not being judged; the surface is not yet entitled.
C Verifier infrastructure unavailable · no receipt issued · status.vitalcv.health Something went wrong · service unavailable · 503 Names the controller (VitalCV) and the status surface. Operators escalate by reading the artifact; HTTP-class phrasing does not name the responder.
D Verified · 0 adverse records · affirmative negative No results · nothing found · no data Verified absence is a finding. SaaS empty-state phrasing reads as failure; institutional phrasing reads as positive outcome.
E Issuer signing key unavailable · σ withheld · backup quorum 2 of 3 armed Signing failed · cannot sign · key error Names the cryptographic plane and the recovery mechanism. The verifier can trust the system because the system names exactly what it cannot currently do.
Language contract
Failure language carries three obligations on every surface: (1) name the plane that owns the failure, (2) name the recovery mechanism or the recovery owner, (3) name what is and is not currently asserted about the subject. SaaS error-class phrasing ("something went wrong," "no results," "failed to load") violates all three. Institutional phrasing reads as operational disclosure, not as user-facing error. The artifact survives a hospital audit because it tells the auditor what it cannot do and who is responsible.
