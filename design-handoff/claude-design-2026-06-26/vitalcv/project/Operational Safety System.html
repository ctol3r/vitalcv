VitalCV · Operational Safety System · v2026.05.21
Evidence-bounded trust. No fake certainty.
Every visible confidence signal must be defensible. No silent failures. No magical continuity. No confirmations beyond the evidence. This document defines six degraded states, three confirmation types, a four-party ownership model, and the recovery arc — for institutional PearX readiness.
§1
Degraded-state hierarchy.
Six named states. The state governs what the operator sees, what copy is shown, and whether action is required. No state is silent about its own existence. Levels 0–1 need no display. Levels 2–5 require explicit UI acknowledgment.
0
Nominal
All sources responding. All records current.
Normal operation. No display needed. Absence of signal is the signal.
No indicator · Level 1 (Ambient) in sidebar sources only
1
Latent
One source slower than usual. No operator impact yet.
Source still responding, but response time elevated. No stale data. No operator action needed. Log internally, do not surface.
No display · internal log only · threshold: response time >30s but within last check window
2
Checking
Source not responding. Last result shown. Retrying.
One source missed its check window. Last valid result is displayed. No operator action required — but must be disclosed. Dashed source bar + age label in sidebar. Attention notice bar if actively viewing affected records.
Dashed source bar · stale age label · attention notice (Level 3) · threshold: 1 missed check window
DEA checking again
DEA last responded 5 hours ago — last result is shown. Resuming automatically. No action needed.
3
Extended gap
Source not responding for 4+ hours. Records noted as aged.
Named callout in the affected stage view. Every affected record must show "Last result from [time]." Operator sees what is and is not confirmed. No auto-advance past this state.
Named source callout in stage view · age shown on every affected record · threshold: >4h without response
4
Multiple sources
Two or more sources not responding. Verification may be incomplete.
Stage-level attention. The stage header must name which sources are affected. No verification can be claimed as complete while multiple sources are down. Operator must acknowledge before advancing.
Stage header warning · named sources · operator acknowledgment required · threshold: 2+ sources at Level 2 or above
5
Decision required
Verification cannot complete automatically. Your decision is needed.
Full recovery panel. Named gap. Four Q&A items (what happened / what's showing / what happens next / what you need to do). One primary action, one ghost. Never called "error."
Full recovery panel · Q&A structure · Level 4 (Decision) trust signal · primary + ghost action
DEA cannot confirm at this time.
Last result from this morning is shown. Two clinicians are affected. Review their records before advancing.
§2
Bounded confirmation patterns.
Three confirmation types. The type must match the evidence. Never confirm more than the evidence supports. If one source is stale, the confirmation is bounded — not silent about the gap.
Full
All sources live
Verified. Licensed and active in all 5 checked registries.
Use when every source has a current, successful result. No qualifiers needed. This is the only state where "Verified" stands alone.
Bounded
One source stale
Verified across 4 of 5 sources. DEA result from this morning is shown.
Must name the gap. Which source, how old the result is. Never say "Verified" without the qualifier when any source is stale.
Honest void
Source unavailable
DEA status cannot be confirmed at this time. Last known result from this morning is shown.
Use when the source has not responded long enough to cast genuine uncertainty. Name the source. Name the last known state. Never omit or hide.
Confirmation grammar rule: "Verified" alone = full confidence, all sources current. "Verified across N of M" = bounded. "Cannot confirm" = honest void. Never use "Verified" with an asterisk, caveat, or footnote — demote to Bounded instead.

§4
Psychological-safety language.
Unsafe copy creates anxiety, distrust, or confusion. The patterns below are psychologically unsafe — they imply failure, alarm, or false certainty. Each has a calm, honest alternative.
Infinite loading / no feedback
Unsafe
Verifying… (spinner, no timeout, no message)
Operator doesn't know if the system is working or broken.
Safe
Checking NPDB. Usually takes a few minutes. Last checked: 2 min ago.
Silent failure
Unsafe
Verified ✓ (DEA result quietly omitted from check)
Operator believes full check passed when it didn't.
Safe
Verified across 4 of 5 sources. DEA result from this morning is shown.
Magical continuity
Unsafe
All records secured on the blockchain. Immutable. Tamper-proof. ✓
Overclaims what the system does; institutional buyers will probe it.
Safe
Records saved. Can be re-checked at any time. Last saved at 2:31 PM.
Theatrical automation
Unsafe
AI is continuously monitoring all sources and automatically resolving discrepancies in real time.
Unverifiable claim; implies capability the system may not have.
Safe
Sources checked every 15 minutes. Results update automatically. Gaps are named when they occur.
Alarm without resolution
Unsafe
⚠ ERROR: DEA ARCOS source failure. Verification incomplete. Action required.
Alarm without guidance causes operator paralysis and escalation anxiety.
Safe
DEA is checking again. Last result from this morning is shown. No action needed — continue reviewing other clinicians.
§5
Continuity-recovery arc.
Five states, one arc. Every recovery is a named, visible progression — not a silent background process. The operator always knows which state the system is in.
State 1 — Nominal
All sources responding.
Silent operation. Sidebar sources show current ages. No notice displayed.
No action · System
State 2 — Checking again
Source missed its check window. Last result shown.
Attention notice bar shown. Dashed source bar in sidebar. Automatic retry every 15 min. Age label on affected records.
No action required · System handling
State 3 — Extended gap
Source not responding 4+ hours. Records aged.
Named callout in stage view. Every affected record shows "Last result from [time]." Gap documented in record notes.
Reviewer should note — may need to acknowledge
State 4 — Decision needed
Cannot advance without reviewer judgment.
Full recovery panel. Q&A structure (what happened / what's showing / what happens next / what to do). One primary action, one ghost. Flow does not advance automatically.
Reviewer must act · primary button shown
State 5 — Recovered
Source responding. Records updated.
Gap documented in record notes. Records updated with new result. Attention notice dismissed. Recovery is named, not silent. "DEA responded — record updated."
System · gap documented
§6
Implementation guidance for Claude Code.
Safety rules — never do these
S1
Never show a spinner without a timeout message. After 30s: show "Still checking — this sometimes takes a few minutes." After 5m: escalate to degraded state 3.
S2
Never confirm what hasn't been checked. If a source is stale, the confirmation must be bounded: "Verified across N of M sources." Never omit the gap.
S3
Never use alarm language without a resolution path. Every attention state must include: what happened + what's showing + what to do (even if the answer is "nothing").
S4
Never auto-advance past a Decision state. If the operator hasn't acknowledged, the flow stays on the recovery panel. No silent progressions.
S5
Never hide a source gap from the operator. Degraded state 2 or higher always surfaces — in the sidebar age label, the attention notice, or both.
Degraded-state detection logic
1
Track lastSuccessfulCheck per source. If age < 1 check window → State 0 (nominal). If age > 1 window → State 2 (checking). If age > 4h → State 3 (extended gap).
2
Count sources in State 2+. If count >= 2 → escalate affected stage to State 4 (multiple sources). Show stage-level attention, not just notice bar.
3
Recovery: when source responds after a gap, emit a named recovery event: "DEA responded — record updated." Show in notice bar for 30s, then dismiss. Log in record notes permanently.
Confirmation boundary logic
1
Before writing "Verified": check all required sources. If any source is at State 2+, demote to "Verified across N of M sources" automatically.
2
For projections: always append "— a projection based on pilot results, not a confirmed outcome." Never let a projected number stand alone.
3
For pilot-scope claims: replace "clinicians" with "these [N] clinicians" and append "in this pilot" for any claim derived from bounded data.
Ownership transition rules
1
When a stage transitions from own-sys to own-rev: the stage header chip changes, the copy switches to active voice ("Review" not "Being reviewed"), and a primary action button appears.
2
When an operator completes a review item: emit confirmation copy specific to what was done: "James Park, DO reviewed. 2 remaining." Never generic "Done!" or "Success!"
3
The deployment decision requires both own-rev (final review) and own-org (authorization). Neither can advance alone. Both must be explicitly checked.
