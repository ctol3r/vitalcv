Verifier trust registry · receipt inspection runtime · canon

What a verifier loads. How a receipt is inspected. Same vocabulary, both ends.

A third-party verifier bootstrapping against VitalCV consumes one signed registry document: issuer DID, signing keys (JWKS), key rotation horizon, trust-registry attestation, and the independent TSA anchor. Once bootstrapped, every receipt the verifier inspects renders the same primitives — signature chain, issuer continuity, verification trace, chronology — without ever calling back to VitalCV. The registry survives our absence.

Verifier bootstrap · 5-step ladder

third-party reaches σ-verifying state without ever calling VitalCV at runtime
STEP 01
Resolve DID
Fetch /.well-known/did.json. Verify TLS chain. Compare against trust-registry-attested hash from at least one independent mirror.
curl https://vitalcv.health/.well-known/did.json
STEP 02
Cross-check registry
Resolve did:web:registry.healthcredentials.org. Confirm VitalCV is admitted as node 0x2e1f with hash 2e1f…cc44. Registry is independent of VitalCV.
vitalcv-verify --registry-check
STEP 03
Load JWKS
Fetch /.well-known/jwks.json. Verify its signature against the kid named in did.json. Cache for 24 h with stale-while-revalidate.
curl https://vitalcv.health/.well-known/jwks.json
STEP 04
Pin TSA anchor
Resolve did:web:tsa.vitalcv.health. Confirm independent key custody — different controller, different operator account. Cache TSA cert.
vitalcv-verify --tsa-pin
STEP 05
Self-test verify
Verify one canonical receipt offline. Expected outcome: σ ok · chain ok · TSA ok · count 0. Failure aborts bootstrap with named error code.
vitalcv-verify --self-test --offline
