Trust-state transitions · four states · no implied verification

What is public. What is verified. What is owned. What is signed.

A credential moves through four distinct trust states. Each state has a contract: what exists, what is signed, what is owned, what a verifier can conclude — and what is explicitly not true yet. The chrome, the boundary chip, and the language all agree at every transition.

Verified ≠ Authenticated
S1 authenticates a person at an IdP. It does not verify anything about a clinical license. Authentication is identity at an inbox; verification is a claim about a fact in the world.
Owned ≠ Signed
At S2 the clinician owns a bound claim and a VitalCV-signed receipt. The receipt is an internal audit artifact. No third party should treat it as a credential — only S3 produces one.
Signed ≠ Currently true
S3 says the issuer signed an attestation at a point in time. Whether the underlying license is valid right now is a runtime question answered by the verifier reading the Status List. Signature is provenance, not currency.

Verifier trust state

five possible verdicts on a signed credential

Once a credential exists (S3), every verifier read produces exactly one of five verdicts. The verdict is a function of the credential, the issuer DID document, the Status List, and the clock — nothing else. No verdict is implied.

Truth rule · no implied verification
At every state, the UI labels exactly which facts are asserted and which are verified. A verified fact is one whose proof can be reconstructed by a third party without VitalCV's cooperation. Everything else is an assertion — and is rendered as such.
Truth rule · no compound signals
A single visual element never combines authentication and verification. The session pill, the binding chip, and the credential badge are three distinct controls — colocated, never merged. If a user is reading one signal, they are reading exactly one signal.
