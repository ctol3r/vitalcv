each flow is operationally complete · not a funnel

The four flows are not stages in a linear funnel. They are operationally distinct contexts — each has its own ownership pattern, completion semantics, and interruption vocabulary. A reviewer may enter any flow at any point. Each flow must be self-contained enough that a new reviewer can orient in under 30 seconds.

01

Completion-confirmation semantics · three patterns

every stage closes explicitly · never silently

A stage is never "completed" because the user navigated away. Every completion is an explicit event — either the user confirms it, the system confirms it, or both. The moment of completion is visible, named, and includes the next step. Completion is never retroactive: a stage that completes while the reviewer is away is shown as "completed while you were away — here's what happened."

04

Bounded simulation language · per flow · pilot vs. production

honest always · never magical · per-flow language

Each flow uses different language when in pilot mode vs. production mode. The language shift is not cosmetic — it reflects a real operational difference. Pilot mode is bounded by the agreed NPI set. Production mode carries the full weight of institutional trust. The reviewer always knows which mode they are in.

Per-flow simulation language · pilot vs. productionboth columns binding
Onboarding
Pilot
"This pilot covers exactly 10 clinicians." Scope is confirmed before start. No extrapolation. The confirm step makes the boundary explicit before any verification runs.
Production
"Adding clinicians to your live roster." Scope is the full org. New clinicians are added to an existing verified set. The boundary is the organization, not an NPI list.
Review
Pilot
"Reviewing 7 of 10 pilot clinicians." Count always shown as X of Y (pilot scope). Exceptions noted as "within pilot scope." Results don't generalize to the full roster.
Production
"Reviewing 3 flagged records across your full roster." Count is absolute. Exceptions may reference prior verification history. Results apply to all credentialing decisions.
Verification-prep
Pilot
"Pilot packet for Dr. Chen — based on 28-day pilot data." Packet header names the pilot. Chain depth is bounded by pilot start date. Labeled "pilot packet" throughout.
Production
"Credentialing packet for Dr. Chen." Full chain depth. Sources are live. Packet is audit-grade. No "pilot" label — this is the actual credentialing document.
Deployment
Pilot
"Pilot complete — ready to confirm production setup." The pilot outcome is evidence, not production. The deployment step is where pilot becomes real. This transition is explicit.
Production
"All clinicians are live on your production roster." No pilot language. This is the operating state. Ongoing verifications run on schedule. No more "pilot" framing.

specific always · never performative · earned by transparency

07

Implementation guidance · Claude Code · binding rules

flows · completion · interruption · simulation · all binding
Completion semanticsexplicit always · never silent · never retroactive
Pattern A (user)
always show a confirm action before advancing · name the reviewer who is confirming · record the timestamp in the audit trail · auto-advance past a user-confirmed completion
Pattern B (system)
always surface the completion timestamp and any caveats · show what completed and what (if anything) was noted · present system completion without a next-step hook
Pattern C (while away)
always label cross-session completions explicitly · always state "nothing was lost" · always show session gap duration · present a cross-session completion as synchronous
Confirm button
show a confirm button when the stage cannot advance — hide it entirely. A disabled button implies "almost there but blocked." A hidden button with a clear "what's missing" message is honest.
Next-step architecturealways present · flow-aware · never generic
Footer position
always render the next-step footer at the bottom of every stage surface · it updates when state changes · hide the footer when the state is auto-advance — show "system is acting" language instead
Flow awareness
The next-step text must be flow-specific. Pass the current flow context (onboarding | review | verification-prep | deployment) to the next-step component. reuse generic "proceed" language across flows
Empty state
render an empty next-step footer — if no action is available, show the auto-advance pattern: "System is acting — you'll be notified when ready." One sentence. No spinner.
Interruption handlingnamed · flow-specific language · never alarming for non-blocking states
Left border
Solid ink-900 = normal · dashed ink-500 = source/format issue · dotted ink-700 = waiting for person · solid s-ok = recovered. always pair border with a plain-English message — border alone is insufficient
Flow language
Source degradation in the review flow: "last result is shown, review can continue." Same degradation in verification-prep: "noted in packet, committee will see it." Same event, different consequence per flow — use flow-specific language.
Alarm calibration
use alarm language for non-blocking interruptions · "DEA is checking again shortly" is informational — not alarming · reserve direct language ("cannot proceed") only for states where the reviewer truly cannot advance
Bounded simulationpilot vs. production · labeled in UI · per-flow language
Mode banner
render pilot or production mode indicator on every institutional surface · data-mode="pilot" or data-mode="production" on root element · banner reads from this attribute
Language fork
Each flow component receives mode prop and renders flow-specific pilot or production language. use the same copy in both modes — the operational difference is real and the language must reflect it
Transition moment
The onboarding-to-deployment arc includes exactly one mode transition: at the deployment confirm step, language shifts from pilot to production. make this transition explicit — name it in the confirm surface
