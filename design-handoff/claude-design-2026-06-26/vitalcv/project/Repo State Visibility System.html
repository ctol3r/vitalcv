00

Materialization state machine · five states · valid transitions only

states are explicit · transitions are deliberate · never implicit

Every wave, route, and surface exists in exactly one materialization state. Transitions between states are explicit decisions — not automatic side effects of code changes. A state transition requires both a code change and an update to the topology map. A wave that transitions without updating the map is a drift event.

Five states · valid transitions · left-border encoding per statebinding · vc.2026.05.21
Spec
Design artifact only. No route. No component. No data. Exists in design docs or wave specs. Not navigable from the product.
Partial
Route exists. Component renders. At least one declared feature or data binding is incomplete. Boundary marker required on surface.
Live
Fully materialized. Route, component, and data all connected. No unbuilt features referenced in UI copy. No mocked data without labels.
Superseded
Higher wave is canonical. File stays in repo. Route is removed. Not imported in app.jsx. // SUPERSEDED by wave{N} comment at file top.
Orphaned
Built but disconnected. No active route. No active import. May exist due to a refactor, abandoned feature, or missed cleanup after supersession.
Valid transitions from Spec
Spec → Partial (build begins)
Spec → Orphaned (built, not wired)
Valid transitions from Partial
Partial → Live (build complete)
Partial → Superseded (wave replaced)
Partial → Orphaned (route removed)
Valid transitions from Live
Live → Superseded (higher wave ships)
Live → Orphaned (route removed without replacement)
Valid transitions from Superseded
Superseded → Orphaned (file confirmed disconnected)
Never: Superseded → Live. Restore means a new wave number.
Valid transitions from Orphaned
Orphaned → Live (reconnected by new wave)
Reconnection always creates a new wave number. No silent restoration.

Wave-state hierarchy · three layers · dependency direction

foundation → views → compositions · always upward

Waves are organized into three dependency layers. Foundation waves provide tokens, primitives, and shared components. View waves build individual surfaces. Composition waves assemble views into flows and prototypes. A wave's state is only as strong as its weakest dependency — a live composition on a partial view is effectively partial.

02

Route binding protocol · four columns · one source of truth

route → component → data → state · all four required

Every live route is bound across four columns: the path, the component it renders, the data it consumes, and its materialization state. A route is only live when all four columns are complete. A route with a component but no data source is partial. A route with a declared path but no imported component is an orphan.

03

Topology synchronization pattern · four steps · run per wave

design → route → component → data · all four in order

Every wave goes through four synchronization steps before its state can be marked live. The steps are sequential — you cannot mark a wave live if any step is incomplete. Running this protocol per wave is what prevents design-reality drift from accumulating.

Sync protocol · four steps · run at wave completion · bindingall four required before live
Step 01
Design audit
Compare the design artifact (HTML spec, wave doc) against the materialized view. Every feature mentioned in UI copy or shown in the design must exist in the component.
All features in design copy are built
No speculative UI elements in the view
Mocked data labeled with // MOCK
Partial features carry boundary marker
Step 02
Route audit
Confirm the route is declared in app.jsx, resolves to the correct component, and is reachable from at least one navigation entry point.
Route declared in router
Component imported (not orphaned)
Reachable from nav (not dead-end)
No superseded file at same path
Step 03
Component audit
Verify the component renders without errors, all props are supplied, all child components are imported, and no TODOs remain in interactive paths.
No console errors on render
All props typed and supplied
No TODO handlers on buttons
All imports resolve (no orphaned deps)
Step 04
Data audit
Confirm every data value comes from a real source or an explicitly labeled mock. Update the route binding table. Set wave state to live.
Real data or labeled mock per field
Route binding table updated
Topology map reflects new state
State machine transition logged
Wave is Live only when all four steps pass. Steps 1–3 pass but step 4 fails = Partial Step 2 fails (no route) = Orphaned Step 1 fails (design only) = Spec
04

Drift detection system · six signals · all fixable

drift is detectable · fixable · never acceptable

Design-reality drift occurs when the design artifact and the materialized implementation diverge without the topology map being updated. Six drift signals cover the most common failure modes. Each signal is detectable by inspection — no automated tooling required, though automation is encouraged.

Drift signals · design → implementation3 of 6
Signal 01 · UI copy references unbuilt feature
"This feature is mentioned in the surface but doesn't exist in the component."
A button label, status message, or section heading describes a feature (e.g., "Bulk revoke") that has no handler or backend. The design spec has it; the component doesn't.
Remove the copy, add a data-materialization="partial" marker, or build the feature before shipping the wave.
Signal 02 · Design artifact links to non-existent route
"Navigation in the design leads to a surface that has no live route."
A design artifact (e.g., a wave spec) shows a nav link to a spec-only surface. If that link is copied into the product, it creates a dead end or 404.
Audit every navigation element in design artifacts before porting to product. Remove links to spec-only surfaces.
Signal 03 · Mocked data unlabeled
"A data value in a live surface is hardcoded without a // MOCK comment."
A clinician count, source status, or timestamp is hardcoded but appears to be live data. The reviewer cannot distinguish real from mocked. This is an honesty failure.
Add // MOCK comment at every hardcoded value. Connect to real data source or mark surface as partial.
Drift signals · implementation → topology3 of 6
Signal 04 · Superseded file still in router
"A superseded view file is still imported in app.jsx with an active route."
wave14-activation.jsx was superseded by wave14b, but the old route still resolves. A user navigating via back-button or direct URL can reach the superseded view.
Remove superseded routes from app.jsx. Add // SUPERSEDED by wave{N} to the file. Update route binding table to orphaned.
Signal 05 · Topology map not updated after wave ships
"The route binding table says Partial but the component is now complete."
A wave completed all four sync steps but the topology map wasn't updated. The map shows partial; the product is live. Anyone reading the map makes a wrong decision.
Update topology map as part of step 4 of the sync protocol. Treat map updates as a required deliverable, not an optional cleanup task.
Signal 06 · Design artifact presented as product surface
"A D44-D55 HTML file is linked from the product navigation."
A standalone design artifact (Why VitalCV, Wave Stack, etc.) is linked from the product's nav bar or sidebar. An institutional reviewer clicks it and lands on a design spec, not a product surface.
Remove all design artifact links from product navigation. Design artifacts are never imported in app.jsx. They are documentation, not routes.

07

Implementation guidance · Claude Code · binding rules

state machine · sync protocol · drift prevention · all binding
State machine enforcementtransitions are decisions · never side effects
State declaration
declare materialization state explicitly on every view component root using data-materialization attribute · infer state from rendering behavior
Transition logging
Every state transition (spec→partial, partial→live, live→superseded) must be accompanied by a topology map update. change a wave's state without updating the binding table
Restoration rule
restore a superseded or orphaned component by removing the supersession comment — restoration requires a new wave number. This creates an auditable record of the change.
Sync protocol enforcementfour steps · all required · per wave
Step 1 (design)
Before declaring a wave complete, read the design artifact and verify every feature mentioned in UI copy is built. ship a wave with UI copy that describes unbuilt features
Step 2 (route)
Verify route is in app.jsx, component is imported, and nav has an entry point. declare live if any of these three are missing
Step 3 (component)
Check browser console on render. Verify all props. Verify all handlers. declare live if any interactive path has a TODO handler
Step 4 (data)
Audit every data value. add // MOCK comment to every hardcoded value. Update route binding table. skip the table update as a cleanup task — it is a required step
Drift preventionsix signals · detectable by inspection · fix immediately
UI copy audit
grep for feature names in UI copy and cross-reference with component handlers before each wave ships · any unbuilt feature mentioned in copy = drift event
Nav audit
audit every nav link in design artifacts before porting to product · link to spec-only or orphaned surfaces from product navigation
Supersession audit
After shipping any wave N that supersedes wave M: (1) remove wave M route from app.jsx, (2) add supersession comment to wave M file, (3) update binding table. ship a superseding wave without completing all three steps
Map freshness
The route binding table and wave hierarchy must be updated within the same commit that changes a wave's state. A stale map is itself a drift artifact.
