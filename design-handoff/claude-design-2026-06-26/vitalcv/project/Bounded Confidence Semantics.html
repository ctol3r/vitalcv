Confidence only to the extent of the evidence.
Four confidence grades, four readiness gates, one source-confidence component. Every visible trust signal must be defensible against the actual evidence available at render time. No inflation. No silence about gaps.
§1
Confidence scale · A–D.
Four grades. The grade is derived automatically from source availability and recency. It governs the copy, the visual treatment, and whether operator action is required.
A
Fully confirmed. All sources current.
Every required source has a successful result within the last check window. No gaps, no stale data, no bounded qualifiers needed.
Verified. Licensed and active in all 5 checked registries.

Verified with noted limitation. One source aged.
All required sources have results, but one is outside its check window. The gap must be named. "Verified" is still usable, but must be qualified.
Verified across 4 of 5 sources. DEA result from this morning is shown.

Checking. Results not yet complete.

§3
Deployment readiness gates.
The deployment decision passes through four gates in sequence. A gate cannot be skipped. Each gate has a condition, a copy template, and a defined action. "Ready" means all gates are clear — nothing more.

Gate B is the normal production state. In a live deployment, some sources will occasionally lag. Gate B allows deployment to proceed while naming the limitation honestly. Gate A is ideal but should not be the only acceptable path.
§4
Degraded-state UX patterns.
Four patterns for source failure, infrastructure outage, stale cascade, and recovery. Each has a named state, a specific visual treatment, and defined copy. Degraded states are never hidden, auto-resolved, or re-labeled as healthy. Use the Tweaks panel to isolate each pattern.
A — Single source unreachable
Unreachable · DEA
DEA cannot be reached at this time.
Connection lost · Last result was 5h 22m ago · Prior result shown in affected records · All dependent clinician records are at Grade D until this source recovers.

Unreachable ≠ Stale. Unreachable means no connection — not an aged result. Grade D applies to all clinicians where this source is required. Copy must say "cannot confirm" — never "no issues" or "last known status."

§5
Evidence-boundary semantics.
Confidence is only as strong as the evidence that produced it. Five boundaries constrain what the system can assert. Every confidence claim must be traceable to a specific source, result, and timestamp. No inference beyond the evidence envelope.
Evidence statement formula
[Source] returned [result] as of [timestamp].
Confidence: Grade [X] · [n] of [m] sources · oldest result [age].
✓ "NPPES confirmed NPI 1346053246 active as of 3 min ago. Grade A · 5 of 5 sources · oldest 3 min."
✗ "Active and verified." — no source, no timestamp, no age, no count
✗ "No issues found." — absence of known issues is not confirmed clean
BoundaryRuleProhibited inference
Age
Confidence cannot be decoupled from result age. A result from 4h ago attests to status 4 hours ago — not now.
"Verified" with no timestamp or expired result.
Source
Confidence in one source cannot substitute for absent confidence in another. Each source must independently confirm.
"Verified" when any required source is absent or unreachable.
Scope
Source X cannot answer a question that requires source Y. NPPES cannot stand in for DEA. Scopes are non-substitutable.
Using a passing source to infer another source's result.
Absence
A non-responding source is not "no issues." Silence must never render as "clean" or "confirmed." Absence is a named gap.
"No issues found" when the check did not run or returned nothing.
Inference
The system cannot project current state from a past result. "Was active 4 hours ago" cannot render as "is currently active."
"Currently active" from any result older than the check window.

§5
Review-accountability chain.
Every deployment decision passes through four accountability steps. The highlighted step is the current owner. No step can be skipped or silently completed.
Step 1
System
Queries all sources. Saves records. Computes confidence grade per clinician.
→
Step 2
Reviewer
Reviews pending items. Judges stale results. Approves or escalates exceptions.
→
Step 3
Org
Authorizes deployment. Signs off on scope. Decision is theirs to make.
→
Step 4
System
Executes handoff. Documents deployment record. Confirms completion.
Step 2 is currently active — reviewer owns the pending items. The workspace header chip shows Reviewer and copy switches to active voice. When step 2 completes, the chain advances to step 3 automatically — visibly, not silently.
§6
Implementation guidance for Claude Code.
Confidence grade computation
1
Grade is computed per-clinician at render time. Input: sourceResults[] with {source, result, age}. Rule: if all age < 1 window and all result = success → Grade A.
2
Grade B: all sources have results, but any age > 1 window. Display bounded: "Verified across N of M sources." Name the stale source(s) explicitly.
3
Grade C: any source has no result yet (check in progress). Show fraction bar. Name the running source. Never say "Verified."
4
Grade D: any source at degraded state 3+ (age >4h) or operator judgment required. Surface recovery panel. Primary action required before advancing.
Readiness gate evaluation
1
Evaluate gates in order A→D. First matching gate determines deployment state. Gate D is evaluated first for blocking issues, then A→C for positive states.
2
Gate B requires explicit reviewer acknowledgment via a UI action. Do not auto-advance through Gate B. The reviewer must see the limitation and confirm they accept it.
3
The deployment decision is a two-party confirmation: reviewer.approved && org.authorized. Neither alone is sufficient. Both must be recorded with timestamp.
Source confidence display rules
1
Bar fill = max(0, 1 - (age / (2 * checkWindow))). Full fill at fresh. 50% fill at exactly 1 check window. Zero fill at 2+ windows. Never show zero for a source with a result — minimum 10%.
2
Badge progression: age < window → "Live". age < 4h → "Checking" (dashed marching bar). age >= 4h → "Stale" (static dashed bar). Never just remove the source row.
3
The marching animation on the DEA bar signals retry activity. It should only animate when a retry is actively in progress. Stop animation when not retrying — use static dashed bar instead.
Accountability chain rules
1
The active accountability step must always be visible. The stage header ownership chip (own-sys / own-rev / own-org) must match the current step. Update it when ownership transitions.
2
When a reviewer completes an action, emit specific confirmation copy: "[Name] reviewed. [N] remaining." Log the action with timestamp. Never generic "Complete."
3
Accountability transitions are always visible: a named event, a chip change, and an updated next footer. No step advances silently in the background without an operator-visible confirmation.
